# Exact Favorite identity resolution: approval proposal

Status: review-only source and contract tests; no endpoint, deployment, client activation, Rules changes, provider activation or new permission has been applied. The frontend preservation hotfix does not depend on this proposal. New Favorites remain unavailable when the ordinary client cannot establish the exact target identity.

The existing `/v1/resolve-favorite-trainer-identity` route is gated by `readProviderPublicShareEnabled`. Activating that shared gate would activate paused provider work, so it is unsuitable for this incident release. Client `users` and `authIndex` reads remain confined to the caller's own records.

The proposed independent capability resolves one exact existing legacy handle to its reciprocal Firebase UID. `exact-resolver.cjs` is the isolated service contract. It is deliberately not a deployable wrapper. Auth verification, consumed App Check verification, distributed quota and scalar data adapters must be supplied by an independently reviewed deployment package before activation.

Proposed HTTP contract: POST `/v1/resolve-legacy-favorite-identity`; JSON body `{ "handle": "ExactExistingHandle" }` only; maximum request body 512 bytes. Verify a non-revoked Firebase ID token and project-bound App Check token with replay protection. Enforce a shared limit of 30 requests per authenticated UID per 15 minutes. Read only `authIndex/<callerUid>/username`, `users/<callerHandle>/authUid`, `users/<exactTargetHandle>/authUid`, and `authIndex/<targetUid>/username`. Require both reciprocal pairs and exact case, and reject self-targets. Return only `{ok:true,targetUid,canonicalHandle}` or the generic unavailable diagnostic. No list, search, names/email inference, credential read, account repair, or account-data write is permitted. Do not log handles, UIDs, tokens, request bodies or raw failures; aggregate outcome counts suffice.

Deployment approval needed: approve preparation and deployment of an independently disabled-by-default endpoint with those exact identity reads, App Check token consumption and bounded distributed quota storage, followed by a separate frontend call-site change. The resource/service identity, region, adapter revision, IAM bindings, quota store/TTL, authorized origins, image digest, activation flag and rollback command must be supplied in a final immutable deployment manifest for approval before any production write or new permission. This document authorizes none of those unspecified details. Existing Firebase Rules and provider/PIN flags remain unchanged. Verify scope with the operator before selecting resources; do not reuse paused provider controls.

Required deployment qualification: ordinary-token browser add/remove from Trainers and shared lists against real Auth/RTDB boundaries and the actual candidate endpoint; unauthorized, revoked, expired, App Check replay, rate-limit, reciprocal mismatch, concurrent identity change, timeout and retry tests; separate-device persistence; exact response and no-private-read assertions. Current four contract tests cover the pure decision boundary only, not those deployment guarantees. Backend identity reads are sequential; a transactional identity snapshot or stable authoritative binding is required in the adapter to address concurrent remaps. A resolver response grants no private-list access; existing share rules remain authoritative.

Live account restoration is a separate approval. For each affected account, first capture owner identity evidence and raw device storage/journal plus canonical records, pending operations, recovery candidates and resolution receipts through existing authorized access. Propose exact candidate IDs and resulting canonical values, excluding tombstones and deliberately resolved records. Never infer ownership, replay completed migrations, or merge every historical backup. No affected-user account has been identified or restored in this investigation.
