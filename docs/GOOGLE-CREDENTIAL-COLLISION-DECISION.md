# Existing-account Google credential collision: source decision

Status: source candidate only. There is **no enabled credential-recovery endpoint, Admin mutation, or Auth blocking policy** in this change. The accepted production baseline remains `.119`. PR #97, PR #130, and Safe-transfer PR #131 remain independent and undeployed.

## Released path and exact failure

On `.119`, signed-out `Continue with Google` (`index.html`, `js/app/application.js:continueWithGoogle`) calls the Google adapter's `signInProvider`, which calls Firebase `signInWithPopup` before `resolveGoogleAccountBinding` checks the canonical foundation and `authIndex/{uid}`. The latter returns `unlinked` when both mappings are absent. `providerAccountCreation` is false by default, so onboarding is rejected and the app signs out. This does not undo the Firebase Auth user that Google sign-in just created. After signing in to the original account by PIN, Settings → Connected Accounts calls `googleAuthAdapter.linkCurrentUser`, which uses `linkWithPopup` on the original user. If Google is already attached to the Auth-only UID, the credential collision denies linking. This path is reachable without enabling provider-account creation. The original PIN account is the account to preserve.

The pre-existing `tests/provider-linking-foundation.test.cjs` injects `auth/credential-already-in-use` into an in-memory owner Map. It proves application denial behavior, not Firebase allocation. The new Auth emulator test uses `accounts:signInWithIdp` with a **synthetic** Google subject and `accounts:signInWithPassword`, and routes the collision through the actual `googleAuthAdapter.linkCurrentUser` handler. The emulator returns HTTP 200 with `errorMessage: FEDERATED_USER_ID_ALREADY_LINKED`; the test's injected REST transport translates that response to `auth/credential-already-in-use`, which the adapter preserves as its safe client error. The Web SDK's conversion of the emulator response is **not** exercised. This is distinct from `auth/account-exists-with-different-credential`; a generic account-merge recipe for that other error is unsafe here. The test does not use a browser Google popup or prove human OAuth behavior.

## Tested mechanic, not an authorized recovery

In the isolated emulator only, Admin `updateUser(orphanUid, {providersToUnlink:['google.com']})` removed the provider but did **not** free the orphan's primary email. A subsequent link returned `EMAIL_EXISTS`. A separate Admin update changed the synthetic orphan's email to an inert test address; then the existing adapter linked Google to the original PIN UID, and subsequent synthetic Google and PIN returns both resolved to that UID. No Firebase user was deleted. This demonstrates that any eventual operation must address **both** provider and email ownership, and that ambiguous Admin results require exact readback. It does not establish that either change is safe for a real UID.

An original-account-preserving recovery would require a recent accepted original PIN sign-in bound to the original UID and healthy account fingerprint, isolated fresh proof of the exact Google provider subject and conflicting UID, explicit one-attempt user consent, and trusted exact readbacks that the conflicting UID has no app account, handle, provider/subject claim, profile/sync/product data, pending operation, alternate meaningful credential, or authorization. Neither matching email nor the collision error supplies that proof. The isolated proof must never activate the conflicting UID as the app's trainer session. An old attempt, wrong original UID, different subject, stale proof, or replacement session must fail. After any credential mutation, the operation would have to read back both Auth users and the subject allocation; it could acknowledge success only after a fresh Google return and PIN return resolve to the original UID with unchanged product/account-sync fingerprints. Retries may only reconcile the **same** subject and UID; they may not chase a new owner.

That protocol is **not qualified by current contracts**. `authIndex/{uid}` absence does not prove absence of a historical `users/{username}` binding because that reverse lookup requires an unknown username. Current trusted readers do not provide a complete, exact, UID-scoped inventory of all legacy bindings, provider claims, private data and in-flight repair/registration state. Even a momentarily empty read would be stale before an Admin Auth update unless all creation/repair writers for that UID and subject are durably excluded and checked at the mutation boundary. Auth and Firestore/RTDB cannot be changed in one transaction. A client lock, an empty UI, a caller-supplied “complete” flag or an in-memory lease cannot close this gap. Missing permissions, missing evidence or an active/ambiguous record mean **not qualified**. A real second app account stays denied; no merge is attempted.

Therefore this candidate intentionally has no path that releases a real credential. The frontend now directs existing trainers to PIN sign-in and Connect Google before a Google-first mistake, and explains that a collision did not erase their original trainer account. This is user guidance, not server-enforced prevention and not repair of already allocated Auth-only credentials. Existing linked-Google return and PIN sign-in remain intact.

## One bounded preventive alternative for review

While provider-account creation remains disabled, a **Google-only `beforeUserCreated` blocking trigger** could reject a new signed-out Google Auth identity before Firebase saves it. It must leave password/PIN creation and sign-in, existing linked Google sign-in, and linking to an existing UID alone. New Google-first onboarding would be unavailable until separately enabled with its own admission policy; already existing Auth-only Google identities would remain and still need a separately qualified recovery. Firebase requires Authentication with Identity Platform for blocking triggers. This is a new Auth control and dependency, not a client flag. It would require a separate exact deployment/configuration review, synthetic trigger tests, current-user impact assessment, rollback plan, and approval. **No such trigger is installed or enabled here.** [Firebase blocking triggers](https://firebase.google.com/docs/functions/auth-blocking-events)

An actual recovery would additionally require trusted UID-scoped orphan evidence, durable exclusion of all competing writers, and narrowly authorized Admin Auth update permission for exact provider and email mutations. Those capabilities are absent from this candidate; no live IAM, Rules, Auth, account or namespace changes were made. [Admin update contract](https://firebase.google.com/docs/reference/admin/node/firebase-admin.auth.updaterequest)

## Review and release administration

The #130 trust model remains: operator signatures authenticate evidence; freshness and revocation also depend on reviewed authority code, route closure and runtime generation repinning. It does not claim resistance to a compromised authority runtime. The prior Codex Security workbench retry failed to inventory committed blob `3019f84:functions/e1-authority-service/durableProviderAdmission.js`; no sealed scan report exists. No repository rule identified in this focused candidate makes that scanner a mandatory merge gate, but any external mandatory sealed-scan requirement remains unmet and cannot be substituted by manual review. The unchanged private first-mutation harness `functions/.local/e1-group-d-reserve-console.js` is unavailable; this PR does not change that contract and does not reconstruct its credentials or claim a live IAM/OAuth qualification.

This candidate's executable evidence is the focused Auth emulator/adapter test and Google UI tests. The emulator test proves only the synthetic mechanics, not eligibility, race safety or human OAuth. It must not be used to authorize live credential release. The next bounded decision is whether to review the single scoped Google creation guard above; actual recovery remains blocked until the exact orphan-evidence and writer-exclusion invariant can be met.
