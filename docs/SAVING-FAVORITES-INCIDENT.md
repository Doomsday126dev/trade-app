## Findings and fixes

1. **Readable wants cannot be edited/removed.** `accountSyncController.snapshot()` prioritized any recovery candidate as `review-required`; `accountSyncProjectionReady()` rejected that state, so mutation admission rejected otherwise valid canonical wants. This reproduces when a returning owner has valid wants and an unresolved unrelated legacy Favorite. The hotfix requires healthy owner/session/schema/listener/controller evidence while admitting review-only baselines. The controller checks each mutation against unresolved local review candidates: other entity types are independent, exactly mapped different trade identities are independent, ambiguous trade evidence blocks trades, matching Favorite UID/name evidence blocks that Favorite, and tag review blocks tag mutations. Conflict, ownership, schema and blocked-operation failures remain closed. Inactive, offline, pending and listener error states now take precedence over review labels.

2. **A second startup race exists.** The Auth callback can run before `doLogin` binds the trainer name. Admission then exits as not ready while the cached list renders. `showApp()` now retries the deduplicated runtime startup once the signed-in product owner is bound. Full ordinary Auth emulator login exposed this; an already-initialized controller fixture would not.

3. **New Favorites fail with own-account reads.** `resolveLegacyFavoriteIdentity()` and the exact identity migration helper expect another trainer's reciprocal private `users`/`authIndex` pair in `allData`. Ordinary sessions cannot read it. The browser fixture stores only its own private identity; direct reads of the other profile/index and their parents return permission denied. Trainers and shared-list mutation entry points both reproduce an unavailable identity without false local success. A previously validated owned canonical Favorite tuple can now survive migration without another private target read. New identity resolution is still blocked; the existing provider resolver is behind a paused shared capability. The independent contract and approval boundary are in `proposals/saving-favorites/APPROVAL.md`. The frontend alone does not fix new Favorite creation.

4. **Legacy Favorites disappear during canonical adoption.** Migration places unresolved identities in recovery candidates; `replaceSyncedOrganization()` replaces local visible Favorites with the canonical projection, which excludes them. That is hidden unresolved evidence, not proof of deletion. The hotfix preserves the exact raw history string once before replacement, retains raw history in the migration source, includes tag links in new unresolved candidates and displays unresolved local Favorite evidence with its available canonical tag labels. It does not claim the evidence is an active synced Favorite or grant list access. An interrupted old migration reuses its exact earlier name-only candidate and fingerprint; completed migrations are not rerun.

5. **Misleading status and retry behavior.** Draft controls remain populated after retryable failure and show a specific waiting/review diagnostic. Canonical Favorite status uses pending/error/acknowledgement state; local organization is still labeled as local. Ordinary online/foreground recovery reattaches only after recognized transport/listener failures, bound to the same Auth object, owner and session generation. It does not auto-repair identity/schema/conflict failures. The local Favorite removal result now reports the mutation's actual success instead of returning a changed state without `ok`.

## Recoverability and limits

Verified synthetic sources include server recovery candidate names, new candidate tag IDs, canonical tags, IndexedDB `legacy-source:<migration id>` snapshots, pending operation journals and the new immutable `:before-canonical-v1` raw-history backup. Old retained migration snapshots can contain Favorite/tag organization even when older name-only candidates omitted tag membership. Older migration snapshots did not retain all raw history; normalization could already prune snapshots for hidden Favorites. The new backup cannot recover bytes that were lost before installation.

A clean second profile correctly receives acknowledged canonical want changes, but does not hydrate another device's recovery journal into the visible preserved section. Server recovery records and old grouped review receipts need separate reconciliation semantics; blindly importing them could resurrect previously resolved records. A different browser, storage partition or account can also explain missing device-only history. Canonical tombstones and deliberate recovery resolutions must remain excluded from restoration. No claim is made that a specific reporter's Favorites are recoverable until their authorized evidence is examined.

Test logs, final CI, review and exact deployment outcome belong to the final incident delivery. Frontend release and affected-user resolution are separate outcomes.

## User-facing explanation

Some older Favorites were kept as recovery information but stopped appearing in the active list. That could also prevent unrelated wants from saving. This update preserves that information and lets healthy, unrelated wants sync again. New Favorites still need a separate backend correction. Please keep the existing app data; do not clear storage or rebuild your lists while account-specific recovery is assessed.
