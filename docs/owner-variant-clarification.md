# Optional owner variant clarification

Only saved generic Spinda, generic Gigantamax Urshifu and Shiny generic Detective Pikachu receive an owner-only entry point. Exact canonical identities do not. The compact My List notice is dismissible, never opens itself and does not block other work. Dismissal is local to the owner/device and survives reload; Options always retains the entry point. A broad request is valid: Keep unspecified changes no trade record.

Choices reuse existing qualified identities and artwork: Spinda Forms1–8/Heart, Single Strike/Rapid Strike Gigantamax Urshifu, Detective Hat2019/Detective2023. No notes, gender, year strings or Shiny-release assumptions select a variant automatically. Existing release labels/early-want policy remain. No artwork, catalogue entries or release assertions are added.

Add exact request copies the complete canonical source values, not the lossy presentation row: priority, variant text, gender, Lucky, sizes, Shiny, background, order, quantity, note and mirror. The target retains the source surface/lane and gets its own valid identity/ID. An existing exact target, including a tombstone, requires review; an expected-generation-zero guard and existing server lifecycle conflict rules prevent rebasing a new copy into a re-add. Mixed aliases require individual review rather than copying only the first record or merging them. Unsaved editor changes must be saved first.

The generic original is untouched by adding the copy. After the existing journal commits the explicit addition, the dialog says Close, original preference controls become read-only and a bounded Check save action is available. There is no new retry loop. Remove original is exposed only after the private sync controller is healthy/saved with no pending/blocked/conflict records, the exact add operation matches an unchanged generation1/revision1 target, its identity and every preference match, and the original's entire canonical record is unchanged. Explicit removal revalidates these facts and uses the ordinary guarded deletion operation; it does not rewrite an ID, redirect aliases or destroy the tombstone/history.

This is a two-stage owner workflow, not an atomic cross-entry move. Closing before admission prevents enqueue. Once journaled, a copy remains pending across closing/offline/restart and is handled by normal sync. A changed account/session or changed source/target cannot authorize the clarification removal. Reopening after restart does not invent a relationship to an already-existing exact request; both are retained for review. Other concurrent owner actions remain independent under the existing transaction semantics; the workflow does not claim cross-entry atomicity.

No cloud request or saved-entry mutation is made by displaying/dismissing the notice or keeping a generic choice. No auth, Rules, backend, billing, permissions or sharing scope changes. Current styling and My List structure remain. EN/ES/DE/JA copy is supplied. Synthetic Playwright fixtures block production account/service/analytics traffic and exercise real local admission, journal, controller and transaction adapters.
